Test results for upstream/tor41350/ (revision 2)
=================================================

Baseline: tor-0.4.9.14 (8fe2745). Build: ./configure --disable-asciidoc
--disable-manpage --disable-html-manual --enable-fatal-warnings, Ubuntu
24.04 x86_64, OpenSSL 3.0, Python 3.13. Every test and lab run was done
offline, inside a network namespace that only has loopback
(unshare -n; ip link set lo up).

Patch
-----

0001-conn-Only-uncount-connections-that-were-counted-as-o.patch   (tor#41350)
  +23/-6 lines of C outside tests and changes/, in 5 files: one bit
  opened_in_rephist in connection_t, set by note_connection() and
  listener_connection_new(); the rep_hist_note_conn_closed() call in
  connection_mark_for_close_internal_() only runs if the bit is set, and
  clears it; connection_ext_or_transition() moves a counted connection
  from the EXT_OR to the OR counters.
  Tests:
    connection/opened_counter (new, test_connection.c), with canaries so
    that the 0 clamp cannot hide a stray decrement:
      - a listener is counted, then uncounted when marked;
      - an accepted OR connection whose (mocked) TLS handshake fails inside
        connection_init_accepted_conn() leaves OR/received unchanged;
      - a counted connection that is marked, then freed, is decremented
        exactly once;
      - marking an uncounted socketless EXIT connection leaves
        Exit/initiated unchanged;
      - the created counter is unchanged.
    extorport/handshake (existing, test_extorport.c), three new assertions:
    the counted Extended OR connection is in EXT_OR before the transition,
    and in OR (not EXT_OR) after it.
  Not covered by unit tests: TransPort (AP) init failure, the DIR side of
  linked BEGIN_DIR and AP+DIR pairs, and outbound directory connections whose
  connect() fails right away. These all take the same mark-without-count path
  as the socketless EXIT case above. The real SSL_accept() failure is covered
  by the lab below.
