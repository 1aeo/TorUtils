# Deliverable 1: Verified Facts, Hypotheses, and Unknowns

## 1. Scope and Methodological Discipline

All findings below were independently verified against the raw artifacts in `/Users/joey/tor/1aeo/private/hsdir-metrics-analysis-20261020` (`BASE`), the unstripped reference builds and symbol maps in `/Users/joey/tor/1aeo/private/begindir-blog-draft-20261016/private-audit/profile-symbolication-20261019` (`SYMBOLS`), the stock `tor-0.4.9.14` source tree in `/Users/joey/tor/1aeo/dos/tor-source-0.4.9.14` (`SOURCE`), the candidate main-loop indexing patch in `/Users/joey/tor/1aeo/private/tor-mainloop-stall-fix-20261018` (`CANDIDATE`), and the 7-patch HS defense stack in `/Users/joey/tor/1aeo/dos/torutils/tor41339-hsdir-defense/patches` (`HS_PATCHES`).

The following methodological rules are enforced throughout:
1. **Per-thread userspace denominators & preserved unresolved shares**: All profile shares use the profiled Tor main thread’s (`TID == PID`) total `cpu-clock:u` sample period (`sample_count * 10,101,010`) as denominator. Unresolved (`[unknown]`) samples are preserved in all denominators and reported explicitly; they are never dropped to inflate resolved function percentages.
2. **Narrower verified instruction loops vs. whole-function totals**: We report both (a) the exact instruction-level cleanup scan loops (`90.471742%` on `sarkodie`) and (b) the broader whole-function totals (`smartlist_remove + connection_free_ = 91.219057%` on `sarkodie`, `14.043733%` on `antglizzy`, `14.664362%` on `joji`).
3. **Request-class accounting discipline**: `BEGIN_DIR - tor_hsdir_request_total` is **not** a valid ordinary-directory request counter because `BEGIN_DIR` counts stream starts (`RELAY_COMMAND_BEGIN_DIR` cells in `connection_exit_begin_conn`), whereas `tor_hsdir_request_total` counts parsed HTTP `/tor/hs/3/...` requests inside `directory_handle_command_get`/`_post` only **after** HTTP header/body parsing and **after** the two defense checks (`hsdir_unknown_prev_hop` and `hsdir_req_reused`), and multiple HTTP requests could theoretically occur per stream or streams can abort before HTTP parsing completes.
4. **Traffic accounting discipline**: Whole-process `tor_net_bytes_total{dir="written"} - tor_net_bytes_total{dir="read"}` is **not** directory-response bytes because whole-process byte counters include all OR circuit relay traffic, consensus fetches, and non-directory traffic on the relay.

* **[FACT-L3] Exact instruction-level attribution on `sarkodie` (`4,282` samples)**:

Notably, the immediately preceding `smartlist_remove(closeable_connection_lst, conn)` at `0x72c9b` (`mainloop.c:346`) recorded **`0` samples** (`0.0000%`), proving that `active_linked_connection_lst` occupancy $A$ was much larger than `closeable_connection_lst` batch size $C$ during each teardown pass.
  2. **Loop 2 (`39.887903%`, `1,708 / 4,282` samples)**: Inlined linear scan inside `connection_free_` (`0x1cd5a0`, loop `0x1cd640..0x1cd64c`) implementing `tor_assert(!connection_in_array(conn))` (`src/core/mainloop/connection.c:970` -> `smartlist_contains(connection_array, conn)` on global RIP-relative `0x3bb8c0`), called from `connection_unlink` (`0x72cc1`).   3. **Why stock Tor used `smartlist_contains(connection_array, conn)` in `connection_in_array()`**: Source inspection of `src/core/mainloop/mainloop.c:290-321` reveals that `connection_remove(conn)` in stock `tor-0.4.9.14` deletes `conn` from `connection_array` in $O(1)$ using `conn->conn_array_index` and updates the swapped tail element’s `conn_array_index`, **but never resets `conn->conn_array_index = -1`**. Because `conn->conn_array_index` remained a stale non-negative integer after `connection_remove(conn)`, `connection_in_array(conn)` could not simply test `conn->conn_array_index >= 0` without first fixing `connection_remove(conn)` to reset `conn->conn_array_index = -1`.
  4. **Additional active-linked list scans on `sarkodie` (`1.891639%`, `81 / 4,282` samples)**:
     * `29` samples (`0.677254%`) in `smartlist_remove(active_linked_connection_lst, conn)` reached via `connection_stop_reading_from_linked_conn` tailcalls from `connection_stop_reading` (`0x1d2fb5`: `21` samples) and `connection_stop_writing` (`0xa3888`: `8` samples).

## 4. Explicit Unknowns (`[UNKNOWN]`)

1. **[UNKNOWN-U1] Actual runtime occupancies $A$, $N$, and $C$ during production floods**:
   * Stock Tor `0.4.9.x` does not export `smartlist_len(connection_array)` ($N$), `smartlist_len(active_linked_connection_lst)` ($A$), or `smartlist_len(closeable_connection_lst)` ($C$). While `sarkodie`’s `50.58%` vs `0.00%` `smartlist_remove` ratio proves $A \gg C$ and `50.58% / 39.89%` suggests $A$ and $N$ were of comparable order of magnitude (thousands to tens of thousands), the exact numeric values of $(A, N, C)$ in production are unknown until Tier 0 gauges are deployed.
2. **[UNKNOWN-U2] Exact HTTP request class and URL family during `>=500 BEGIN_DIR/s` floods**:
   * Because the 4 `tor_hsdir_*` counters were only deployed on `youngdro` and `pouya` (which had `0` flood episodes) and all profiled floods (`sarkodie`, `antglizzy`, `joji`) occurred on stock relays, we do not know what fraction of flood `BEGIN_DIR` streams carried `/tor/hs/3/...` requests, ordinary `/tor/server/...` or `/tor/status-vote/...` requests, malformed HTTP headers, or pre-HTTP stream aborts.
3. **[UNKNOWN-U3] Whether `sarkodie`’s low outbound rate (`27.19 Mbit/s` at `5,585 BEGIN_DIR/s`) was attacker-driven (tiny/aborted requests) or self-inflicted by the `92.36%` main-loop cleanup stall**:
   * When the main thread spends `92.36%` of its userspace CPU inside linear connection-list scans, `active_linked_connection_lst` read/write transfers and socket flushes are starved, which can itself suppress outbound throughput and cause client timeouts/aborts. Only a post-patch observation under flood can separate attacker request size from main-loop starvation.
